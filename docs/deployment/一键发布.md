# 一键发布

本文档是 AI Learning Tutor 深度开发期间的测试环境发布入口。它用于把尚未
合并的、已经审查通过的功能分支精确版本发布到测试服务器，供产品负责人
实际操作学习软件。测试完成后先恢复原版本，再创建功能 PR；不得先合并
功能代码再测试。

测试站点：<https://learn-app.dy.dywxgz.com/>

日常发布不要求产品负责人安装 Docker、执行命令、接触服务器，或者保管
SSH、镜像仓库和数据库凭据。Codex 应按照本文档完成技术操作，并只把需要
实际体验的页面和测试重点交给产品负责人。

## 以后只需要这样提醒 Codex

开发批次完成并通过独立审计后，可以直接发送：

```text
请按 docs/deployment/一键发布.md 执行：把刚完成并审计通过的版本发布到
测试服务器。我不操作命令；发布后打开测试页面并告诉我本批要测试什么。
在我回复“测试通过”或“测试有问题”前，不要回滚，不要创建或合并功能 PR。
```

测试结束后发送下面二者之一：

```text
测试通过。按一键发布文档回滚测试环境，验证恢复，再为功能分支创建 PR；
不要自行合并功能 PR。
```

```text
测试有问题：<描述看到的问题>。按一键发布文档保存必要证据并回滚测试
环境，不要创建功能 PR，回到原功能分支修复。
```

不要在提示词或聊天中发送账号密码、验证码、token、GitHub Secret、SSH
私钥、镜像仓库凭据或数据库内容。需要登录学习软件时，产品负责人只在浏览器
登录页面自行输入测试账号。

## 执行者需要什么，不需要什么

需要：`gh` 已登录本仓库，以及一个能读取测试服务器的 SSH 通道用于核验。

不需要：本机 Docker、本机 `docker login`、镜像仓库密码。镜像由 GitHub
runner 构建为 `linux/amd64` 并交给服务器现有 registry 登录推送。本机是 arm64
的 Mac 也不影响。不要因为"要发布"就去启动本地 Docker Desktop。

## 固定发布顺序

每个开发批次必须遵循同一个顺序：

```text
功能分支开发完成
-> 自动测试和独立审计通过
-> 锁定远端分支上的完整 40 位 commit SHA
-> 确认该 SHA 的 CI 全绿
-> 同步服务器侧配置与价格目录（本批需要时）
-> 一键发布到测试服务器
-> 完成服务器核验和浏览器冒烟测试
-> 产品负责人实际体验
-> 发现问题需要发修复版时：先一键回滚，再用新 SHA 重新发布，回到上面一步
-> 一键恢复发布前版本
-> 验证恢复后的服务状态
-> 测试通过才创建功能 PR
-> 等待代码审查和 CI，不自行合并功能 PR
```

测试版本必须来自远端分支上的精确 commit，不得使用未提交的本地文件、分支
名称当前指向或浮动 tag 代替完整 SHA。

## Codex 执行清单

以下步骤由 Codex 执行。产品负责人不需要运行其中的命令。

### 1. 发布前闸门

发布前必须确认：

- 功能分支已有独立审计放行结论；
- 待发布 SHA 是完整 40 位值，且真实存在于远端分支；
- 功能分支工作树干净，已有提交不得被 amend 或悄悄替换；
- 分支 CI 全绿，集成测试为零失败、零跳过，并达到该 SHA 自己定义的门槛；
- `main` 保持干净，功能分支尚未合并，功能 PR 尚未创建；
- 明确本批是否包含 `server/migrations/` 变更；
- 明确本批是否需要新的服务器侧配置或新的价格目录行，见下一节；
- 测试服务器当前 tag、服务健康状态、可用磁盘和现有测试发布状态已读取；
- 服务器上没有处于 `STATUS=DEPLOYED` 的测试发布，否则先回滚；
- 没有另一场发布或回滚正在运行。

任一条件不成立时停止发布，说明具体阻塞。不得为了得到绿色结果而放宽测试、
跳过备份、改 CI 门槛、直接推 `main` 或临时关闭安全检查。

闸门可以这样读取：

```sh
# 待发布 SHA 的 CI 结论；必须是 completed success
gh run list --repo oppositenum/learn-app --commit '<完整 40 位 SHA>' \
  --json databaseId,name,status,conclusion

# 服务器当前 tag、健康状态和测试发布状态
ssh root@bt.dy.dywxgz.com 'cat /opt/learn-app/.test-release-state; \
  docker ps --filter name=ai-learning-tutor --format "{{.Names}}\t{{.Image}}\t{{.Status}}"; \
  df -h /opt | tail -1'
```

### 1.1 服务器侧配置不在工作流范围内

这是最容易漏的一步。Test Deploy 只做 `status`、`upload`、`deploy` 三件事，
它**不会**修改服务器上的 `compose.yaml` 或 `.env.production`。而
`/opt/learn-app/compose.yaml` 只存在于服务器上，仓库里没有对应文件，所以
代码里新增一个环境变量时，没有任何仓库侧改动会提醒你去同步它。

本批新增或改名了 API 读取的环境变量时，发布前必须在服务器上完成两件事，
缺任何一件，变量都会静默地到不了容器，应用会以为"没配置"而降级或直接不
启用该功能：

1. 在 `compose.yaml` 的 `api` 服务 `environment:` 下加入透传条目；
2. 在 `.env.production` 写入取值，并保持 `chmod 600`。

改动前先备份，改动后用 `docker compose config` 确认插值正确：

```sh
ssh root@bt.dy.dywxgz.com 'cd /opt/learn-app && \
  cp -a compose.yaml compose.yaml.bak-$(date +%Y%m%d-%H%M%S) && \
  cp -a .env.production .env.production.bak-$(date +%Y%m%d-%H%M%S)'

# 校验插值；只看变量名，不要把带密钥的整段配置打印到日志或聊天里
ssh root@bt.dy.dywxgz.com 'cd /opt/learn-app && \
  docker compose --env-file .env.production -f compose.yaml config' \
  | grep -E "^      [A-Z_]+:" | sed -E "s/((KEY|TOKEN|PASSWORD): ).*/\1<hidden>/"
```

含 JSON 的取值在 `.env.production` 里按原样写、不要加引号，compose 会正确
解析成单行字符串。

### 1.2 新增 AI Provider 或 Model 时必须先写价格目录

每次 AI、STT、TTS 调用在联网前都要通过 `ai_price_catalog` 价格预检，
找不到当时生效的 `(provider, model)` 行就返回 `ErrPriceNotFound`，**一个网络
请求都不会发出**。所以切换或新增 provider/model 时，价格行必须在发布前
写入生产库，否则服务健康、页面正常，但每一次教学生成都失败。

用仓库脚本按受控汇率换算生成 SQL，再在服务器上执行；脚本只打印 SQL，不
连接数据库：

```sh
bash scripts/generate-ai-price-catalog-sql.sh --help
# 生成后
scp prices.sql root@bt.dy.dywxgz.com:/tmp/prices.sql
ssh root@bt.dy.dywxgz.com 'cd /opt/learn-app && set -a && . ./.env.production && set +a && \
  docker compose -f compose.yaml exec -T postgres \
  psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -v ON_ERROR_STOP=1 -q < /tmp/prices.sql && \
  rm -f /tmp/prices.sql'
```

汇率取值、来源和生效日期记录在 SQL 注释里，不要硬编码进业务逻辑。

### 2. 触发 Test Deploy

工作流定义必须从 `main` 运行，但 `commit_sha` 填的是待测试功能分支的完整
SHA。GitHub Actions 页面操作如下：

1. 打开仓库的 **Actions** 页面。
2. 在左侧选择 **Test Deploy**。
3. 点击 **Run workflow**，分支选择 `main`。
4. `commit_sha` 填待测试版本的完整 40 位 SHA。
5. `release_name` 填小写发布名称，例如 `b3-safety-audit`。
6. `confirmation` 填大写的 `DEPLOY`。
7. 点击绿色 **Run workflow**。

也可以用 GitHub CLI 触发同一个工作流，参数和安全边界不得改变。用工作流
文件名而不是显示名，显示名改了也不会失效：

```sh
gh workflow run test-deploy.yml --repo oppositenum/learn-app --ref main \
  -f commit_sha='<完整 40 位 SHA>' \
  -f release_name='<小写发布名称>' \
  -f confirmation=DEPLOY
```

`--ref main` 指的是工作流定义从哪里读取，和被发布的代码无关：`commit_sha`
填功能分支的 SHA 即可，该分支不需要、也不应该先合并到 `main`。

工作流自动生成不可混淆的镜像 tag：

```text
test-<release_name>-<UTC日期>-<短SHA>
```

同一天用同一个 `release_name` 重新发布同一个 SHA 会生成相同 tag，网关会以
`requested test tag is already active` 拒绝。换 `release_name` 或换 SHA。

### 2.1 测试期间要发修复版：必须先回滚再发布

测试中发现问题、修好之后想把修复版发上去时，**不能直接再跑一次 Test
Deploy**。服务器网关在已有活跃测试发布时会直接失败：

```text
ERROR=a test release is already active; run rollback first
```

正确顺序是：

```text
Test Rollback（恢复发布前 tag）
-> 确认 STATUS=ROLLED_BACK
-> Test Deploy（新的 SHA、新的 release_name）
```

回滚**不会**恢复或删除数据库内容：网关只切换镜像 tag、重新拉取、重启并
验证健康，`BACKUP_FILE` 只是回显发布前备份的位置，输出里的
`SCHEMA_ROLLBACK=not_performed` 就是这个意思。测试期间产生的数据、以及
发布前写入的价格目录行，都会保留。不要因为担心丢数据而跳过回滚。

### 3. 等待全部自动门禁

Test Deploy 会依次完成：

```text
锁定精确 SHA
-> Go vet 和 Go 单元测试
-> 真实 PostgreSQL 集成测试
-> 按目标 SHA 的 ci.yml 检查 PASS 门槛、FAIL=0、SKIP=0
-> Web 测试、lint 和 build
-> 构建 API 与 Web 的 linux/amd64 镜像
-> 校验镜像架构和 org.opencontainers.image.revision
-> 上传镜像归档到受限服务器网关
-> 由服务器现有登录推送私有镜像仓库
-> 检查服务器原版本和健康状态
-> 备份 PostgreSQL，并验证备份可读取
-> 切换测试 tag，运行 migration，启动 API 和 Web
-> 验证 PostgreSQL、API、Web、HTTP 和 WebSocket 入口
```

测试、构建或镜像校验失败时，工作流不会修改测试服务器。服务器阶段失败时，
受限网关会在可行的情况下自动恢复原镜像 tag。任何红灯都应先检查该次 run
日志；不得不分析原因就连续重试。

### 4. 发布成功后的独立核验

工作流全绿不代替独立核验。Codex 必须分别报告并核对：

- Actions run 链接、状态和所有 job 结果；
- 请求的完整 SHA 与两个镜像的 revision 标签完全一致；
- API 和 Web 使用相同测试 tag，且均为 `linux/amd64`；
- API 和 Web 各自的不可变 `sha256` digest；
- 发布前 tag、当前 tag，以及受限状态文件中的测试状态；
- 数据库备份文件名、非零大小，以及 `pg_restore --list` 可读取；
- 本次应应用的 migration 均出现在 `schema_migrations`；
- migrate 容器成功退出，日志包含 `database migrations applied`；
- PostgreSQL、API、Web 均为 `healthy`；
- `/app-health` 返回 `ok`；
- API 容器内 `/healthz` 返回 `{"status":"ok"}`；
- WebSocket 路径已上线，并且未认证访问仍被拒绝；
- 公网 HTTPS 页面能正常加载。

本批改动了 Tutor Provider 配置时，还要确认：

- 容器内确实拿到了本批新增的环境变量；
- API 启动日志里没有 `configure ...` 开头的致命错误。生成方与审核方解析出
  相同 `provider:model` 身份时进程会启动失败，这是设计如此的 fail closed；
- 配置指向的每个 `(provider, model)` 在 `ai_price_catalog` 里都有当时生效的行。

```sh
ssh root@bt.dy.dywxgz.com '
  cat /opt/learn-app/.test-release-state
  docker ps --filter name=ai-learning-tutor --format "{{.Names}}\t{{.Image}}\t{{.Status}}"
  docker inspect $(docker ps -q --filter name=ai-learning-tutor-api) \
    --format "revision={{index .Config.Labels \"org.opencontainers.image.revision\"}}"
  docker exec ai-learning-tutor-api-1 env | grep -E "^TUTOR_" \
    | sed -E "s/(API_KEY=).*/\1<set>/" | sort
  docker logs ai-learning-tutor-api-1 2>&1 | tail -20
  docker exec ai-learning-tutor-api-1 wget -qO- http://127.0.0.1:8080/healthz'
```

核验镜像 revision 时要和请求的完整 SHA 逐字符比对，短 SHA 相同不算通过。

有 migration 时，发布前备份是硬门。镜像可以自动恢复，但数据库迁移是
forward-only，恢复旧镜像不会自动撤销表、列、约束或索引。

### 5. 浏览器冒烟测试

服务器健康不等于功能正确。Codex 应在浏览器打开最新带 cache-busting 参数
的页面，避免旧标签页继续显示缓存资源，并至少验证：

1. 登录状态和对应角色首页正常；
2. 本批修改的入口、页面和主要操作能够到达；
3. 学生端、家长端或 Owner 端的未修改导航没有意外变化；
4. 需要实时能力的页面可以连接 WebSocket；
5. 学生 API 和页面没有暴露标准答案或私有答案字段；
6. 冒烟产生的活动课堂在离开时已暂停或按本批预期收口；
7. 不为证明页面可用而提交无关数据、完成真实任务或破坏现有测试夹具。

冒烟结束后把浏览器停在适合产品负责人开始测试的页面。若浏览器已有旧标签，
应明确指出哪个是最新测试页，避免在缓存旧页面上得出结论。

### 6. 交给产品负责人实际测试

Codex 的交付说明必须使用普通中文，至少包含：

- 可点击的测试站点链接；
- 当前运行的完整 SHA 和测试 tag；
- 本批具体需要操作的页面和场景；
- 哪些现象表示通过，哪些现象需要立即反馈；
- 已完成的自动验证和浏览器冒烟结果；
- 明确说明“当前保持测试版本在线，尚未回滚，功能 PR 尚未创建或合并”。

在产品负责人回复“测试通过”或“测试有问题”之前，Codex 不得擅自回滚，
不得创建或合并该功能分支的 PR。

### 7. 测试结束后执行 Test Rollback

无论测试通过还是失败，都要恢复 Test Deploy 记录的发布前镜像 tag：

1. 打开仓库的 **Actions** 页面。
2. 在左侧选择 **Test Rollback**。
3. 点击 **Run workflow**，分支选择 `main`。
4. `confirmation` 填大写的 `ROLLBACK`。
5. 点击绿色 **Run workflow**。

也可以运行：

```sh
gh workflow run test-rollback.yml --repo oppositenum/learn-app --ref main \
  -f confirmation=ROLLBACK
```

回滚只在 `STATUS=DEPLOYED` 时可用。已经是 `ROLLED_BACK` 再跑会以
`there is no active successful test release to roll back` 失败，这不是故障。

回滚后必须确认：

- `RESTORED_TAG` 等于发布前 tag；
- `REMOVED_TEST_TAG` 等于本次测试 tag；
- PostgreSQL、API、Web 均为 `healthy`；
- `APP_HEALTH=ok`；
- `API_HEALTHZ={"status":"ok"}`；
- 公网测试站点仍正常打开；
- `SCHEMA_ROLLBACK=not_performed` 已明确记录。

`SCHEMA_ROLLBACK=not_performed` 是正常且重要的提示：回滚只恢复应用镜像，
不会破坏性地反向执行 migration。数据库确实异常时，不得自行 drop 数据；
应保留发布前备份，由管理员先在隔离实例验证恢复方案。

### 8. 根据实际测试结果处理功能分支

测试通过时：

1. 回滚和恢复后健康检查全部通过；
2. 确认功能分支 SHA 未在测试期间发生漂移；
3. 推送尚未推送的提交；
4. 创建以 `main` 为 base 的功能 PR；
5. 把测试 SHA、Test Deploy run、镜像 digest、备份、migration、浏览器实测和
   Test Rollback run 写入 PR 描述；
6. 等待 PR CI 全绿并通知作者审核；Codex 不自行合并功能 PR。

测试失败时：

1. 记录复现页面、角色、步骤、预期和实际结果，避免记录学生答案正文；
2. 保存必要的 Actions run 和最小化服务日志证据；
3. 执行 Test Rollback 并验证恢复；
4. 不创建功能 PR；
5. 回到原功能分支修复，重新完成自动测试、审计和本文档全部流程。

## 日常只需要记住的五件事

```text
发布的是审计通过的完整 SHA，不是一个会移动的分支名。
工作流不改服务器配置：新环境变量要自己同步 compose.yaml 和 .env.production。
换 provider 或 model 就先写价格目录行，否则一个请求都发不出去。
一键发布全绿后仍要实际操作学习软件。
要发修复版先回滚再发布；测试通过后才创建功能 PR，不自行合并。
```

## 常见失败对照

| 现象 | 含义 | 处理 |
| --- | --- | --- |
| `a test release is already active; run rollback first` | 服务器上已有 `STATUS=DEPLOYED` 的测试发布 | 先跑 Test Rollback，再重新 Deploy |
| `requested test tag is already active` | 同一天同 `release_name` 同 SHA 生成了相同 tag | 换 `release_name` 或换 SHA |
| `there is no active successful test release to roll back` | 状态已是 `ROLLED_BACK` | 无需处理，不是故障 |
| 服务全部 healthy，但教学生成每次都失败 | 多半是价格预检 fail closed，或环境变量没进容器 | 查 `ai_price_catalog` 行；查 `docker exec ... env` |
| 页面功能像是"没配置" | 变量写进了 `.env.production` 但 `compose.yaml` 没透传 | 补 `environment:` 条目后 `docker compose up -d` |
| 构建阶段失败 | 门禁或镜像校验没过，服务器未被改动 | 读该次 run 日志，不要盲目重试 |

## 一次性基础设施

仓库已提供：

```text
.github/workflows/test-deploy.yml
.github/workflows/test-rollback.yml
deploy/learn-app-test-release
deploy/install-test-release-gateway.sh
```

GitHub `test` Environment 保存专用 SSH Secret 和服务器地址变量。测试服务器
使用无交互 shell、无 Docker 组成员身份的 `learnapp-deploy` 账号，只能通过
受限 gateway 执行 `status`、`upload`、`deploy` 和 `rollback`。GitHub 不保存
私有镜像仓库密码，镜像由服务器使用已有 registry 登录推送。

如果 Environment Secret、服务器公钥、gateway、registry 登录或域名发生
变化，应由管理员恢复一次性基础设施。不得把临时凭据写进 workflow、文档、
Issue、PR、Actions 输入或聊天，也不得为了绕过故障改成 root 交互式 SSH。
